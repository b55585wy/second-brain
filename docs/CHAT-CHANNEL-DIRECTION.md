# 学习聊天与飞书接入方向

2026-10-29 设计草案，尚未实现、安装桥接器或发送飞书消息。飞书继续作为可选接口通道。当前 0.2.0 的交付范围见 [简化目标](SIMPLICITY.md)。

## 决策依据

“换成聊天窗口就会更简单”是待验证假设。聊天能够收发消息，但学习仍需要明确的目标、可追溯材料、独立输出及持续记录。日常可用时间和模型预算有限；每换一个入口，不应重复维护目标、练习或费用账本。

因此由知行保存学习状态，网页、聊天客户端与飞书只调用同一组能力。新增聊天入口的验收应比较操作时间、主动输出完成率和无辅助迁移表现；消息数量不代表学习效果。把整段 Codex 对话持续转发进机器人，会增加上下文和配置成本，无法单凭转发实现这条学习闭环。

## 用户能得到的流程

用户选择的时间收到一个简短提醒，打开后只有一道与目标相关的练习；可以直接回答、稍后处理或暂停提醒。保存回答后记录输出，先给本地自查提示；需要更深入反馈时才显式消耗模型预算。来源按需展开，完整管理仍可回到网页。

提醒直接发送已保存的题目，不调用模型；不把提醒频率等同于知识提炼频率。发送记录、答案、练习状态和费用共用现有后端，跨入口继续同一次练习。优先验证一个人的私聊，再考虑群聊、多平台和商业部署。

## Chatbox 的两种含义

| 入口 | 建议实现 | 已核实边界 |
| --- | --- | --- |
| 知行内的聊天窗口 | 在现有首页增加直接回答与少量明确操作，复用现有 today、attempt、feedback 接口 | 现有表单已能保存输出；自由聊天、流式对话和聊天提醒未实现 |
| Chatbox AI 独立客户端 | 提供少量 MCP 工具，如读取今日练习、保存答案、读取进度 | [官方 MCP 文档](https://docs.chatboxai.app/guides/mcp)确认自定义服务及安装链接；尚未验证知行适配、原生飞书同步或主动推送 |

MCP 的写入工具仍须校验练习 ID、档案版本、调用者和幂等操作 ID。首次进入客户端后不要求用户每天编提示词；若宿主必须靠开放式提示才能找到今日题目，就需要进一步验证是否真的减少操作。

## 飞书桥接项目能复用什么

[cc-connect](https://github.com/chenhg5/cc-connect)已支持把本地 Codex 等代理接入飞书等通信平台，[飞书文档](https://github.com/chenhg5/cc-connect/blob/main/docs/feishu.md)说明长连接接入。可以评估复用通信适配；是否可直接用作知行适配器仍需代码验证。只有个人练习收发时，也可直接使用飞书 SDK 调用知行接口，避免额外维护多代理配置。

`feishu-codex-bridge` 有多个同名仓库，不能假定是同一个实现。已核对的 [lengjingxu 版本](https://github.com/lengjingxu/feishu-codex-bridge)使用本地长连接和 Codex app-server，将项目群、话题与会话映射，可参考会话路由、状态卡及重启恢复。学习入口只需读取题目、保存答案与取得反馈；通用本机编码执行应作为独立的可选能力。

[飞书事件文档](https://open.feishu.cn/document/uAjLw4CM/ukTMukTMukTM/event-subscription-guide/event-subscriptions)说明长连接和事件重投。设计上先持久化入站事件并按 event_id 去重，再执行写入或模型调用；投递使用稳定的用户、练习和通道键，失败重试不重新选题或评分。先绑定一个允许用户，仅申请私聊收发所需权限，扩展能力时再增加范围。

本地方案要求电脑、网络与桥接进程持续运行。若要电脑关机后仍可在手机学习，需另行部署常在线学习服务，或云端缓存已生成的题目并与本地采集器同步；这会引入账号、同步和部署工作，不属于当前一键桌面启动的能力。

## 实施顺序与完成条件

先使用当前三重点加一练习流程，确认内容值得学、输出能坚持；再选择一个聊天入口，完成读取同一题目、只保存一次答案、暂停提醒及失败恢复。确认能够减少操作后，再决定复用 cc-connect、扩展更多平台或部署常在线服务。知行保留自己的学习核心，入口可以替换。
